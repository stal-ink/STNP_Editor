# STNP 0.9 冻结计划

> 定位：0.9 落地的**唯一入口文件**。合并阶段一交付物（报错处理机制、配置拆分与 Schema、IR 生成侧与 CLI、GUI 清理与命名、0.9 规格变更清单）与用户裁定表。
> 基线：STNP Editor 0.8.2；目标：STNP 0.9。
> 取向：**破坏性、无兼容、单一落地批次**。
> 目标规范：0.9 结构规范（冻结版）。
> 配套：0.9 规格变更清单（与本计划口径一致；示例处置、内部资源文件去留、批次划分、破坏性取向不得冲突）。

## 2. 破坏性声明

0.9 是一次**破坏性重构**，取向贯穿全文。以下四点同时成立，不可分割：

1. **无兼容层。** 不提供任何读取旧工程、旧配置、旧字段的中间层。
2. **无 shim。** 不提供任何形态的垫片、别名转发或双写桥接。
3. **无弃用告警。** 不输出「字段已弃用」「请改用某某」一类过渡提示；旧用法直接失败。
4. **`additionalProperties: false` 直接拒绝旧格式。** 读到旧字段即失败，不做任何适配。

具体处置：

| 旧形态 | 处置 |
|---|---|
| `.stnp` 内的 `generation` | 不再识别；`.stnp` schema 已删该属性，出现即校验失败 |
| 整数 `schema_version` | 不再识别；类型已改为 string 枚举，出现即校验失败 |
| 复数 `targets` 与双套目标形态 | 整体删除；只认 build 文件顶层单一 `target` |
| `modules[].handler_mode`、`.stnp` 的 `groups` | 整体删除；出现即校验失败 |
| `features.notify_dispatcher`、`features.crc.runtime_toggle` | 整体删除；出现即校验失败 |
| `notifications[].kind` | 整体删除；出现即校验失败 |
| 缺省目标取值、按目标取配置的派生路径 | 整体删除；目标缺失即校验失败 |

## 3. 批次划分

### 3.1 定案：只允许一个批次

**0.9 的全部改动合并为单一破坏性落地批次**，一次落地、一次验证、一次提交。

### 3.2 理由：示例重写与 schema 变更必须同批

- 若把示例重写与 schema 变更拆开，schema 已删 `generation`、而示例仍带 `generation`，示例将**直接校验失败**，golden 基线无法运行，验证链断裂。
- 同理，通知去分类、CRC 与 SEQ 裁定若与 schema 变更分拆，示例中的 `kind`、运行时开关等字段会立即触发 `additionalProperties: false` 拒绝。
- 因此，示例重写、schema 变更、协议裁定、IR 与生成侧改动、GUI 清理、golden 重生成**必须同批落地**，否则任何中间态都无法通过校验。

### 3.3 取消二分批次

**取消**原先的二分提交方案。原方案假设「配置来源变更不改变生成产物、协议裁定才改变生成产物」，从而可分别提交、分别归因 golden 差异；该假设在破坏性 schema 下不成立——配置来源变更本身即改变示例文件的可解析性，无法作为独立可验证的中间态。故：

| 原方案 | 本计划 |
|---|---|
| 分两次提交 | **单一批次**，一次提交 |
| golden 分两轮处理（一轮零改动、一轮重生成） | golden **一次重生成** |
| 示例先删字段、后重写 | 示例**一次重写到位** |

## 4. 设计定案

### 4.1 报错处理机制

#### 4.1.1 报错分级

| 级别 | 语义 | 影响退出码 | 呈现 |
|---|---|---|---|
| `error` | 阻断性失败，当前命令无法继续，产出不可信 | 是 | `文件:行:列: error[错误码]: 消息` |
| `warning` | 可继续，但结果可能非预期 | 否 | `文件:行:列: warning[错误码]: 消息` |
| `note` | 纯信息，如统计、被跳过对象 | 否 | `文件:行:列: note[错误码]: 消息` |

规则：

- 只有 `error` 参与退出码判定；`warning` 与 `note` 即使存在也不改变退出码。
- `warning` 与 `note` 的启用来自 build 文件的 `validations` 段（字段 `id` / `level`，默认全列全启用）；某校验项以 `warning` 级呈现且不再阻断。
- 本轮不为任何报错点预设 `warning` 默认值；全部报错点默认 `error`。

#### 4.1.2 错误码分段

| 段 | 含义 | 段内范围 | 归属阶段 |
|---|---|---|---|
| `E1xxx` | 加载格式 | `E1001–E1099`（`E1001–E1050` 输入解析，`E1051–E1099` 配置与环境） | 加载期 |
| `E2xxx` | 校验 | `E2101–E2199`（名称与重复、取值范围、引用完整性、路径安全） | 校验期 |
| `E3xxx` | 构建 | `E3001–E3099` | 构建期 |
| `E4xxx` | 生成写出 | `E4001–E4099`（分派、SDK、路径安全、写出、模板） | 生成期 |
| `E9xxx` | 内部 | 仅 `E9001`（未捕获异常）、`E9002`（内部不变量破坏） | 任意阶段兜底 |

规则：

- 形式固定为 `E` 加 4 位十进制；首位为段号。
- 已分配错误码**只增不改**；删除报错点时其码位保留，不复用。
- 本轮错误码总数 70（E1 段 14、E2 段 35、E3 段 7、E4 段 12、E9 段 2）；其中 `E1006` 为 schema 文件缺失预留，本轮不启用。
- 规划新增 5 个加载期错误码：`.stnp` 版本标识不受支持、build 文件缺失或不可读、build 版本标识不受支持、build 文件 schema 校验失败、build 文件 `target` 缺失或非法。

#### 4.1.3 编译器风格输出

- **单条诊断**：位置前缀（文件、行、列）加级别、错误码与消息；默认打印出错行 1 行，并以 `^` 指向列；存在可执行修复建议时附单行 help，否则整行省略；多条诊断之间空一行分隔。
- **多错误排序**：文件字典序（无文件者排最后）→ 行升序 → 列升序 → 错误码升序 → 发现顺序稳定排序。
- **位置省略**：错误不对应具体源位置时省略行列，只输出文件与诊断；连文件都没有时以内部哨兵标识；位置不完整时按可用部分输出。
- **消息**：中文一句话，以事实结尾，不带句末句号。

#### 4.1.4 退出码映射

| 来源 | 错误码段 | 级别 | 退出码 |
|---|---|---|---|
| 加载失败 | `E1xxx` | error | 1 |
| 校验失败 | `E2xxx` | error | 1 |
| 构建失败 | `E3xxx` | error | 1 |
| 生成失败 | `E4xxx` | error | 1 |
| 内部缺陷 | `E9xxx` | error | 3 |
| 用法错误 | 无错误码（命令行解析库） | error | 2 |
| 任意 `warning` / `note` | 任意 | warning / note | 不改变（默认 0） |
| 成功 | — | — | 0 |

补充规则：

1. **退出码 2 只来自 CLI 用法层**，由命令行解析失败触发，不携带错误码；业务侧的非法目标不再走 2。
2. **退出码 1**：出现任意 `E1` / `E2` / `E3` / `E4` 的 `error` 级诊断即返回 1；`check` 的 golden 不一致亦返回 1。
3. **退出码 3 的兜底**：最外层捕获非统一异常后按内部错误呈现并返回 3；内部不变量破坏主动抛出亦返回 3。
4. **判定时机**：在所有诊断收集完毕之后；多段同时出错时取最严重者，内部错误优先于失败。
5. 键盘中断不映射为 3，交还 shell 处理。

#### 4.1.5 报错点归并

| 项 | 结论 |
|---|---|
| 现状显式报错点 | 57 个（加载期 6、校验期 36、构建期 7、生成期 8） |
| 现状隐式报错点 | JSON 解析、schema 校验、文件读写、模板渲染、写出等底层异常，按阶段登记 |
| GUI 目录报错点 | 显式 14 个、异常捕获 32 个，随目录整体删除 |
| 规划新增报错点 | 5 个（见 4.1.2） |
| 分支归并 | 删除复数目标校验与「目标不支持 → 退出码 2」；非法目标改由加载期 schema 枚举校验拒绝，归入退出码 1 |
| 统一载体 | 各阶段异常类型携带错误码、级别、文件、行列、JSON 指针、消息与 help；诊断呈现层负责格式化、排序与批量输出 |

### 4.2 配置拆分与 Schema

#### 4.2.1 两文件职责

| 文件 | 承载字段 | 校验 |
|---|---|---|
| `.stnp` | `format` / `schema_version` / `project_name` / `protocol` / `global_results` / `common_types` / `modules` / `instances` | 独立 schema，`additionalProperties: false` |
| `stnp.build.json` | `format` / `build_schema_version` / `target` / `c` / `python` / `output_stem` / `emit_readme` / `validations` / `layout` / `sdks` / `python_sdks` | 独立 schema，`additionalProperties: false` |

- 两份文件各自持有 `format` 与版本标识；互不引用、互不嵌套。
- 不做旧格式适配：不读取 `.stnp` 内的 `generation`。
- CLI 只按 build 文件的单一 `target` 分派。

#### 4.2.2 根必填变更

| 项 | 动作 | 依据 |
|---|---|---|
| `generation` | 从根 required 与 properties 整体删除 | D8 |
| `global_results` | 加入根 required；新增属性，`minItems 1`，条目 required `name` 与 `value` | D1 / D14 |
| 其余 5 项 | 不变 | 配置拆分补充裁定二 |
| `common_types` | 仍可选，不进 required | — |
| `additionalProperties: false` | 保留 | — |

变更后根 required：`format` / `schema_version` / `project_name` / `protocol` / `modules` / `instances` / `global_results`。

#### 4.2.3 字段归属变更

| 字段 | 原位置 | 新位置 |
|---|---|---|
| `target` | `generation.target` | build 顶层，必填单选 |
| `c` / `python` | `generation.c` / `generation.python` | build 顶层 |
| `output_stem` | `generation.output_stem` | build 顶层 |
| `emit_readme` | `generation.emit_readme` | build 顶层 |
| `emit_examples` | `generation.<target>.emit_examples`（另有内部资源全局项） | build 的 `<target>.emit_examples`，默认 `false` |
| `sdks` / `python_sdks` | `generation.c.sdks` / `generation.python.sdks` | build 顶层选择列表 |
| 输出目录命名 | 内部资源文件 | build 的 `layout.output_dir_names` |
| 示例产出开关 | 内部资源文件全局项 | build 的 `<target>.emit_examples` |

删除项：`targets` 复数；`generation_target` 与 `generation_targets` 双套形态合并为单一 `target`；顶层 `build_system` / `sdks` / `emit_examples` 等旧形态及其全部派生路径。

#### 4.2.4 内部资源处置

**定案：内部资源文件不整体并入 build 文件，按「内部资源 / 用户可调项」二分处置。**

| 类别 | 键 | 处置 | 去向 |
|---|---|---|---|
| 内部资源 | schema 定位、schema 文件名映射、模板目录、内部目录命名、C SDK 注册表、Python SDK 注册表 | 留下 | 生成器内部资源文件 |
| 用户可调项 | 输出目录命名 | 迁出 | build 的 `layout.output_dir_names` |
| 用户可调项 | 示例产出开关（全局项） | 迁出 | build 的 `<target>.emit_examples` |
| 文件本体 | 内部资源文件 | 保留 | 不删除；仅承载上述内部资源 |

理由：

1. **安全边界**：schema 与模板定位属实现资源，交由用户误改会使生成器故障且无法归因。
2. **职责边界**：内部资源回答「生成器怎么实现」，不属工程语义与生成选择。
3. **稳定性**：SDK 注册表随生成器版本演进，暴露后会锁死生成器重构。
4. **对 D9 的正确解释**：D9 意图是消除用户侧第二份配置来源，而非交出生成器实现资源；「内容并入」解释为「用户可调内容并入」。
5. **注册表与选择列表**：build 只放「选了哪些 SDK」的选择列表，注册表留内部；加载期由注册表向选择列表注入枚举。

命名消歧：build 顶层 `sdks` / `python_sdks` 是**用户选择列表**；内部注册表同名不同义，阶段二建议将内部注册表键更名以消歧。

| 维度 | `schema_version` | `build_schema_version` |
|---|---|---|
| 所属文件 | `.stnp` | `stnp.build.json` |

规则：

#### 4.3.2 构建语义

| 项 | 定案 |
|---|---|
| Payload 超限 | 载荷累计完成后，长度超过 `max_payload` 即抛错；该位置为生成侧唯一强制点（确认现状已符合，无需代码改动） |
| Return Code 分段 | `0x0000` 工程级 OK；`0x0001..0x00FF` Global；`0x0100 + 256*i` 起每 Module 256 值；每 Module 强制存在名为 `OK` 的 Return Code 且落在本区间；Module 数 ≤ 255；每 Module Return Code ≤ 256 |
| 工程级码表 | 必填、`minItems 1`；必须存在名为 `OK` 且值为 `0x0000` 的条目；其余条目值落在 `0x0001..0x00FF`；条目数 ≤ 255 |
| 帧长矩阵 | Task 头 = 2 + [2 SEQ] + 1 TARGET + 1 CMD + 1 LEN，SEQ 关/开 = 5/7；Notify 头 = 2 + [2 SEQ] + 1 SOURCE + 1 NOTIFY + 2 RESULT + 1 LEN，SEQ 关/开 = 7/9；CRC 尾 = 0/2 |
| 最大帧 | 取 Task 与 Notify 两家族较大者，加 `max_payload` 与 CRC 尾 |
| RX Ring | 按 4 个最大帧预留 |
| CRC 覆盖 | 固定为 HEADER 至 PAYLOAD 的 body；CRC 自身以 u16 小端追加在 body 之后，不覆盖自身（确认现状已符合）；删除运行时开关后，CRC 存在性只由 `features.crc.enabled` 决定 |
| SEQ 门控 | 新增门控标志默认 `false`；Task 与 Notify 共用同一门控与同一发送方计数器；关闭时 SEQ 槽完全不存在 |
| 目标解析 | 删除复数与派生路径；只读 build 顶层单一必填 `target`；非法或缺失由 schema 枚举在加载期拒绝 |
| 单实例便捷宏 | 直接删除，不做生成侧派生；用户统一使用实例 ID 宏 |
| 符号校验 | 统一入口按目标分派到 C 分支与新增 Python 分支；规则清单来自 build 的 `validations` 段；C 分支删除通知分类宏与单实例 ID 宏相关声明 |

#### 4.3.3 通知去分类

- **语义**：`ACCEPT` / `REJECT` / `PUSH` 不再分类；接受与拒绝语义由 Notify 帧的 `RESULT` 槽承载。
- **保留**：`notify_on_done` / `notify_on_accept` / `notify_on_reject` 保留为触发时机；引用校验退化为「引用的通知存在即可」；自动通知的阶段常量与发送逻辑保留（属触发时机生成代码）；零载荷约束保留。
- **删除**：通知分类字段、分类数值映射、分类宏、通知分组结构及其枚举后缀；C 侧分类注释、分类宏与固定符号表条目；Python 侧通知描述符的分类形参与属性、模块定义中的分类实参；schema 中通知分类必填与枚举。
- **宏名新规**：通知枚举成员、通知表与符号表三处一致的命名改为「模块名 + NOTIFY + 通知名」，不含分类。

#### 4.3.4 校验函数形态

| 项 | 定案 |
|---|---|
| 粒度 | 按模块一个校验函数，由生成器自动生成 |
| 分派 | 按命令码分支分派 |
| 自动校验 | `validate_hook` 为真时，按字段类型与 `min` / `max` 自动产出校验代码 |
| 生成位置 | C 侧生成到 Implementation；Python 侧生成到模块定义文件内 |
| C 侧形态 | 签名与现有校验回调一致（接收实例句柄、命令码、载荷指针）；分支内将载荷转为对应命令载荷结构，按基础类型值域与 `min` / `max` 校验；通过返回本模块 `OK`，失败返回拒绝码或参数错误结果码；接线改为调用生成的校验函数 |
| Python 侧形态 | 按命令码分支分派；通过返回模块结果 `OK`，失败返回拒绝码；分发处改调用生成的模块校验函数；装饰器注册仍保留供用户覆盖 |
| 用户区段 | 本轮不开放（D21 记为后续工作） |

#### 4.3.5 分发 API

- **配置**：新增 `protocol.options.notify_dispatch_receive.enabled`（boolean，默认 `false`，允许运行时切换）；语义为**本端是否启用 Notify 接收分发路径**。
- **组级区分**：`features` 是 Capability（改 wire format、两端一致、禁运行时切）；`options` 是本端行为（不改 wire format、两端可不同、允许运行时切）。
- **API**：新增启用、禁用、查询三支运行时 API；C 侧生成到 Core 的 Notify 头与源文件，Python 侧生成到运行时模块并在包入口同名导出。
- **消费点**：C 侧实例文件的编译期门控改为运行时查询门控，分发路径按开关放行；Python 侧分发分支按查询放行；初值来自协议配置，生成期写入、运行时可切。

## 6. 验收标准

| 编号 | 验收项 | 判定 |
|---|---|---|
| V1 | 破坏性 | 无兼容层、无 shim、无弃用告警；`additionalProperties: false` 直接拒绝旧格式 |
| V2 | 单批次 | 全部改动一次落地；golden 一次重生成；不存在二分批次 |
| V3 | 报错机制 | 三级分级；错误码分段；编译器风格输出；退出码 0/1/2/3；非法目标归入退出码 1 |
| V4 | 配置拆分 | 两文件各自独立校验；根 required 删 `generation` 增 `global_results`；内部资源文件保留 |
| V5 | 版本标识 | 两个版本标识必填、string、独立支持列表；列表外直接抛异常；不进入中间表示 |
| V6 | 协议 | 通知去分类；CRC 覆盖 body 且无运行时开关；SEQ 门控与共享计数器；Return Code 分段 |
| V7 | IR | 8 删 4 增；头长按组合；符号校验按目标分派 |
| V8 | 生成侧 | 校验函数按模块生成并接线；Notify 分发三支 API 落地 |
| V9 | CLI | build 参数必填；单一 `target` 分派；退出码符合契约 |
| V10 | GUI | 目录、入口、依赖、专用字段、测试、文档全部清除；GUI 之外无引用 |
| V11 | 示例与 golden | 3 个 `.stnp` 与 3 个 build 文件齐备；2 个 golden 基线树一致 |
| V12 | 命名 | 最终文件夹名公式成立；无双重命名冲突 |
| V13 | 文档 | 0.9 规范与现行文档同步完成 |
| V14 | 自检 | 全文无行号引用、无代码符号、无兼容表述（除破坏性声明的否定式） |
